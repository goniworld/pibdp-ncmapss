## 0. 위치와 원칙

1. **모든 분석은 탐색 분석이다.** v1.0 시험 결과와 v1.1 결과를 본 뒤에 설계했다. p값과 신뢰구간은 사전 등록 가설의 검정이 아니다.
2. **v1.0 V0는 바뀌지 않는다.** 여기서 시험하는 변형(재가중, 보정)이 V0보다 나아 보여도 V0를 바꾸지 않는다. "개선 가능성"으로만 보고하고, 새 자료에서 검증해야 한다고 적는다.
3. **설정을 다시 조정하지 않는다.**
   - PI-BDP는 v1.0 `config.json`의 기준모델, n_h, λ, k를 그대로 쓴다.
   - 비교 모델은 v1.1과 같은 공개 코드와 원 논문 설정을 쓴다. 적은 자료에 맞춘 조정은 하지 않는다.
4. **시험 데이터의 사용을 구분한다.**
   - WS1(학습 곡선)과 WS2(합성 실험)는 **시험 데이터를 쓰지 않는다.**
   - WS3는 이미 본 시험 예측값을 다시 채점하는 것이므로, 결과 옆에 그 사실을 적는다.
5. 실행한 모든 설정, 실행, 지표를 보고한다. 이 문서와 다르게 실행한 것은 "추가본 이탈"로 기록한다.

## 2. WS1 — 개발 데이터 학습 곡선

### 2.1 자료
- 개발 엔진 60대 중 고장까지 관측된 55대만 쓴다.
  - 고장 전에 관측이 끝난 5대는 학습과 채점 모두에서 뺀다. 그래야 "고장 엔진 수 m"의 뜻이 분명하다.
  - 서브셋별 고장 엔진 수: DS01 4, DS02 6, DS03 9, DS04 4, DS05 5, DS06 6, DS07 6, DS08a 9, DS08c 6
- 시험(test) 엔진은 열지 않는다.

### 2.2 설계
- **바깥 고리:** 서브셋마다 고장 엔진을 하나씩 평가용으로 뺀다(모든 55대가 한 번씩 평가 엔진이 됨).
- **학습 크기 m:** 남은 고장 엔진 중 m대로 학습한다.
  - m ∈ {2, 3, 5, 전체}에서 남은 수보다 작은 값만 쓴다.
  - "전체"는 남은 고장 엔진 모두이다.
- **추출:** m대를 고르는 조합 중 최대 3개를 고정 시드(2026)로 뽑는다. 조합이 3개 이하면 모두 쓴다. "전체"는 하나이다.
- **시나리오**
  - **S-target (주):** 모든 모델이 그 서브셋의 m대만으로 학습한다.
  - **S-pool (보조):** 데이터 기반 모델에 유리한 현실 조건이다. 다른 기종이나 운용 조건의 이력은 많고, 대상 기종의 고장만 적은 경우에 해당한다.
    - TSMixer가 **다른 8개 서브셋의 개발 엔진 전체**와 대상 서브셋의 m대로 학습한다.
    - 레이블은 각 창이 속한 서브셋의 η = 5% 상한을 쓰고, 학습 설정(최적화, epoch, 배치)은 S-target과 같다. 여러 서브셋을 섞어 학습하는 것은 원 코드에 없는 우리의 확장이므로, 바꾼 데이터 로더를 diff로 남긴다.
    - m = 2만, 추출 1개(2.2절 규칙의 첫 조합), 평가 엔진 55대 모두
    - PI-BDP는 서브셋별 함대 모델이라 S-target과 같은 결과를 쓴다(다른 서브셋 자료를 쓰지 않음).

### 2.3 모델
| 모델 | 출처 | 설정 |
|---|---|---|
| PI-BDP V0 | 이 연구 | v1.0 그대로(곱 재가중). 함대 사전분포, 임계값, Weibull을 학습 m대로만 추정 |
| PI-BDP noWeibull, melding α = 0.5, α = 1 | WS4 정의 | 위와 같고 재가중만 다름 |
| GB | v1.0 같은 정보 기준선 | v1.0 설정 |
| TSMixer | CruiseBench `ef26d40` | v1.1 3.2절 설정(η = 5% 상한, 창 256, 간격 10, 50 epoch, 배치 512). 추출마다 시드 1개(시드 = 추출 번호 + 1) |
| TCN | 같음 | 같음 (S-target만) |

- **m이 작을 때 PI-BDP의 처리 (미리 정함).** 이 처리는 v1.0 설정을 바꾸는 것이 아니라, 추정이 불가능할 때만 쓰는 대체이다. 쓰였으면 모두 기록한다.
  - 함대 공분산 Σ_θ: 학습 엔진 수가 매개변수 수 이하(m ≤ 3)이면 표본 공분산이 특이하다. 이때는 대각 성분(분산)만 쓴다. v1.0의 축소 λ는 그대로 적용한다.
  - 고장모드 수: v1.0에서 k = 2인 서브셋에서 어느 모드든 학습 엔진이 2대 미만이면 k = 1로 적합한다.
  - Weibull: m = 2여도 그대로 최대우도로 적합한다. 수렴하지 않으면 재가중 없이(noWeibull) 계산한다.
- 데이터 기반 비교 모델로 TSMixer와 TCN을 쓴다. E2c에서 가장 정확했던 두 모델이다.
- bayesrul(HNN·DE)은 쓰지 않는다. 원 설정이 여러 서브셋을 묶은 모델 하나이고, 한 번 학습에 T4로 1.5–7시간이 들었기 때문이다(E2c 실행 기록). 학습 곡선의 수백 번 학습에는 맞지 않는다.

### 2.4 채점 (평가 엔진 1대마다)
- **주 채점:** v1.1 4.2절 규칙.
  - CruiseBench 순항 창과 η = 5% 상한 레이블
  - PI-BDP는 t − 1 출력 − 1
  - 첫 사이클 창은 모든 모델에서 뺌
  - 모든 예측에 [0, 상한]
- **보조 채점:** 사이클 단위, 상한 없음(v1.0 방식). PI-BDP와 GB만 해당한다.
- **PI-BDP 예측구간:** 보정 전 분위수로 90% 포함률, 폭, interval score, 분위수 9개 pinball을 계산한다. 학습 엔진만으로 정하는 보정은 m이 작으면 불안정하므로 하지 않는다.

### 2.5 지표와 통계
- RMSE: 평가 엔진마다 추출 평균을 낸 뒤, 엔진들을 묶어 통합 RMSE를 계산한다.
- m마다 PI-BDP V0와 각 모델의 RMSE 차이를 계층 붓스트랩(서브셋 → 평가 엔진, 100,000회)으로 구한다.
- **역전점:** m을 키워 가며 차이의 신뢰구간이 처음으로 0을 포함하거나, PI-BDP 쪽으로 불리하게 0을 벗어나는 m을 보고한다.
- 서술은 v1.1 9절의 신뢰구간 규칙을 따른다.

### 2.6 계산량 규칙 (시간만 사용)
- 점검 실행(6절)에서 TSMixer 한 번 학습의 시간을 재서 전체 GPU 시간을 추정한다.
- 한도는 **40 GPU시간(L4, 약 68 컴퓨팅 단위)**이다. 문서를 쓸 때 두 계정에 남은 단위(약 80개)에서 CPU 작업과 여유분을 뺀 값이다. 모든 GPU 실행은 L4에서 한다.
- 미리 센 학습 횟수(서브셋별 고장 엔진 수와 2.2절 규칙으로 계산)
  - S-target: 모델당 415회. E2c 실행 시간으로 대략 추정하면 TSMixer 약 12시간, TCN 약 12시간이다.
  - S-pool: 55회. 한 번 학습 자료가 S-target의 약 8배라 약 20시간으로 본다.
- 한도를 넘으면 다음 순서로 줄인다.
  1. S-pool 평가 엔진을 서브셋마다 엔진 번호가 작은 3대로 줄임(55 → 27)
  2. S-target 추출 수 3 → 2
  3. S-target에서 m = 3 제외
- 어떤 성능 지표도 보지 않는다. 줄였다면 이탈로 기록한다.
- GPU는 L4로 한다(CruiseBench는 최신 torch라 L4에서 동작함).

## 3. WS2 — 합성 데이터 실험

### 3.1 생성 모형 (반합성)
- 서브셋마다 v1.0이 개발 엔진 전체로 추정한 함대 값을 "참값 모집단"으로 쓴다.
  - 경로 사전분포 (μ_θ, Σ_θ)
  - 관측 잡음 σ_e
  - 임계값 (μ_D, σ_D)
- 엔진마다 θ와 D를 뽑고, 식 (5)의 경로가 D에 닿는 시점을 고장 시점으로 한다. 관측은 매 사이클의 HI에 잡음을 더한 것이다.

### 3.2 시나리오
| 기호 | 내용 |
|---|---|
| G0 | 모형이 맞음 |
| G1 | 경로 모양이 틀림: 열화 시작점이 있는 꺾인 직선 경로로 생성하되, 서브셋별 수명 분포의 평균과 표준편차를 G0와 맞춤 |
| G2 | 관측 잡음 2배 |
| G3 | 학습 엔진의 관측을 100사이클에서 중도절단 |

### 3.3 설계
- 학습 엔진 수 m ∈ {2, 3, 5, 10, 20}
- 반복 200회. 반복마다 학습 엔진 m대와 평가 엔진 100대를 새로 뽑는다(시드 고정).
- 평가 시점: 평가 엔진의 수명 25%, 50%, 75% 시점
- 서브셋 9개 모두
- **계산량 규칙:** 첫 서브셋·첫 시나리오 10회의 시간으로 전체 CPU 시간을 추정한다. 24시간을 넘으면 반복을 100회로 줄인다.

### 3.4 방법
- PI-BDP 재가중 4변형(noWeibull, 곱 = V0, melding α = 0.5, α = 1)
- **기준(oracle):** 참값 모집단을 알 때의 사후분포. 참 사전분포를 쓴 같은 계산이다.
- GB: 합성 HI 특징으로 학습한 단순 데이터 기반 모델(v1.0 GB와 같은 특징 구성)

### 3.5 지표
- RMSE, 90% 포함률, interval score, CRPS
- 기준 사후분포의 RUL 분포와의 1-Wasserstein 거리

### 3.6 확인할 것 (WS4의 예측)
1. 곱 재가중(V0)이 melding보다 구간이 좁고 보정 전 포함률이 낮은가
2. m이 작을 때 재가중의 이득과 위험이 각각 얼마인가
3. 모형이 틀린 G1에서 포함률이 얼마나 떨어지는가

## 4. WS3 — 예측구간 보정과 정보 시점

### 4.1 WS3a — 보정 방식 비교
v1.1 A2와 E2b에서 보정 구간이 서브셋에 따라 너무 좁거나(DS02, DS07) 너무 넓었다(DS01–DS05, 포함률 0.995). 원인을 다음 보정 방식들로 살핀다.

| 기호 | 보정 | 정하는 자료 |
|---|---|---|
| C0 | v1.0 그대로: 전 서브셋 공통 c_α (V0) | v1.0 Phase 1b |
| C1 | 서브셋별 c_α | 그 서브셋의 개발 LOUO 예측값(Phase 1) |
| C2 | 예측 RUL 구간별 c_α (Mondrian): 예측 중앙값을 개발 예측값의 삼분위로 나눈 세 구간 | 개발 LOUO 예측값 |
| C3 | 한쪽 하한 보정: 하한만 따로 보정해 "실제 RUL < 하한"의 비율이 5%가 되게 함 | 개발 LOUO 예측값 |

- **보정 상수는 모두 개발 데이터로만 정한다.** Phase 1b와 같은 비적합 점수, 같은 유한표본 보정, 같은 가중을 쓴다.
- **개발 데이터 안의 확인:** C1–C3의 포함률을 개발 LOUO에서 교차 확인한다.
  - C1, C2: 한 엔진을 빼고 정한 상수로 그 엔진 확인
  - C3: 같은 방식으로 하한 아래 비율 확인
- **시험 데이터:** v1.0 고정 시험 예측값에 C0–C3를 적용해 다음을 서브셋별, 수명 구간별로 보고한다. 이미 본 시험 데이터라 **기술 통계로만** 쓰고 검정하지 않는다.
  - 포함률, 폭, interval score
  - 실제 RUL < 하한 비율

### 4.2 WS3b — E2 정보 시점 규칙의 민감도
v1.1 4.2절은 사이클 t의 창에 "t − 1 출력 − 1"을 쓴다. 이 규칙이 결론을 좌우하는지 확인한다.
- 대안 R1: t − 1 출력 그대로(−1 없음)
- 대안 R2: t 출력 그대로(그 비행이 끝난 뒤의 정보를 쓰는 낙관적 규칙)
- E2b, E2c(CruiseBench, bayesrul)의 저장된 예측값으로 다시 채점한다. 같은 붓스트랩으로 RMSE·interval score 차이를 구하고, 9절 표현이 바뀌는 비교가 있는지 보고한다.
- 새 학습은 없다.

## 5. 결과 보고 원칙 (결과를 보기 전에 정함)

1. 모든 m, 시나리오, 모델, 보정 방식의 결과를 싣는다.
   - 본문: WS1 학습 곡선 그림(RMSE, S-target과 S-pool), WS2 요약 그림(보정 전 포함률과 Wasserstein 거리), WS3a 서브셋별 포함률 표
   - 나머지는 부록
2. **PI-BDP가 어떤 m에서도 데이터 기반 모델보다 낫지 않으면**, "적은 고장 이력에서의 장점"을 주장하지 않고 그 결과를 그대로 보고한다.
3. 재가중 변형이나 보정 방식 중 하나가 V0보다 나아도 V0를 바꾸지 않는다(0절 2).
4. WS1은 PI-BDP의 설계 선택에 쓴 개발 데이터로 평가한 것이라 PI-BDP에 약간 유리할 수 있다. 이 한계를 결과 옆에 적는다.
5. WS3a의 시험 결과는 이미 본 데이터의 재채점이다. "보정 개선의 가능성"으로만 쓴다.

## 6. GPU 노트북의 점검 실행 (v1.1 실행에서 배운 것)
v1.1 E2c 실행에서 로컬 시험(CPU, 가짜 데이터)으로 못 잡은 오류가 세 번 났다(실행 기록 9–11번). 그래서 GPU 노트북은 커밋 전에 다음을 실제 데이터, 실제 GPU에서 확인한다.
1. 환경 설치와 GPU 인식
2. 학습 1회를 2 epoch로 실행
3. 일부러 중단한 뒤 이어서 학습
4. 예측 파일 저장과 채점 셀까지 실행
- 점검 실행은 개발 데이터만 쓴다.
- 출력하는 것은 시간과 오류 여부뿐이고, 성능 지표는 출력하지 않는다.
- 점검 실행의 결과 파일은 본 실행 전에 지운다.
