# 프로토콜 v1.2 실행 기록과 이탈 사항

v1.2 부록(커밋 f01eecf82f5bc45ed9a90d44d8361b8dcb217d63)을 실행하면서 생긴 일과, 부록에 적힌 것과 달라진 점을 순서대로 적는다. 모든 WS는 탐색 분석이며, 개발(dev) 데이터만 쓴다.

## WS1 학습 곡선

1. **GPU 노트북 커밋 시점 (2026-11-02).** GPU 노트북은 GPU 스모크 시험(`SMOKE = True`)을 하기 전에 커밋했다. 스모크 시험은 통과했고, 노트북은 고치지 않았다. 그래서 커밋한 판이 그대로 본 실행에 쓰였다(실행 주소 a37f0bd).

2. **GPU 실행.** 계산량 규칙의 추정은 약 32.7 GPU시간(L4)이었고, 계획은 `full`이다(추출 415개, 줄이지 않음). Colab 세션이 끊겨 다른 계정에서 이어서 돌렸다. 저장된 적합 파일은 건너뛰므로 결과는 같다. 적합 885/885개를 마쳤다.

3. **Weibull 재가중이 정의되지 않은 사이클 (채점 중 발견, 2026-11-05).**
   - **증상:** CPU 결과 3개 추출에서 V0, meld0.5, meld1의 점수가 NaN이었다. noWeibull과 GB는 정상이었다. 그중 2개는 S-pool 비교에 쓰는 m = 2, 첫 추출이다(DS05 엔진 4, DS06 엔진 5).
   - **원인:** 학습 엔진이 적으면 표본 Weibull 적합의 형상 모수가 매우 커질 수 있다. 그러면 어떤 사이클에서 모든 표본의 Weibull 로그 밀도가 −∞가 되고, 재가중 가중치가 0/0이 된다. 적합 단계의 실패 검사(모수가 유한한지)는 이 경우를 잡지 못한다. 동결된 v1.0 코드도 같은 계산을 하므로, 이 문제는 동결 코드의 성질이다.
   - **이전 채점의 오류:** 첫 채점 노트북은 엔진마다 추출을 평균할 때 NaN을 건너뛰었다. 그래서 해당 엔진의 V0는 다른 모델보다 적은 추출로 평균되었다. 또 S-pool 붓스트랩의 신뢰구간이 NaN이 되었고, 표현이 기본값("comparable")으로 떨어졌다. 그 판의 결과(실행 a37f0bd의 `ws1_summary.txt`)는 쓰지 않는다.
   - **조치:** v1.2 2.3의 "Weibull 실패 → noWeibull" 규칙을 사이클 단위로 적용한다. 가중치가 정의되지 않은 사이클만 같은 표본을 재가중 없이 쓴다. 저장된 사이클 예측(`raw/`)에서 해당 추출만 다시 채점한다.
     - 다시 채점하는 코드는 먼저 해당 서브셋의 모든 추출에서 저장된 noWeibull·GB(그리고 NaN이 아닌 V0) 점수를 재현해야 한다.
     - 수리 내역(추출, 변형, NaN 사이클 수, 첫 NaN 사이클)은 `ws1_repairs.csv`에 남긴다.
     - 민감도 분석으로, 수리한 추출을 모든 모델에서 함께 빼고 같은 검정을 다시 한다(`ws1_tests_excl_repaired.csv`).
     - 붓스트랩 입력이나 결과에 NaN이 있으면 노트북이 멈추도록 검사를 넣었다.
   - GPU나 CPU 학습은 다시 하지 않는다.

4. **m = 5의 서브셋 수.** m = 5 평가는 고장 엔진이 많은 서브셋 2개(DS03-012, DS08a-009)에서만 가능하다. 서브셋 2개로 하는 계층 붓스트랩은 신뢰구간이 불안정하므로, m = 5의 검정은 서술용으로만 보고한다.
